# Уточнение измерителя таймеров

Исходный валидатор требовал неотрицательный `lagMs`. Сами запросы планируются с дробной задержкой через Node `setTimeout`. На первой полной паре все индексы, число событий, виды и номинальные фазы совпали, но часть фактических запусков произошла на доли миллисекунды раньше тика. Исходный валидатор отверг эти отрицательные значения.

Независимый `qe-primary` подтвердил механизм именно версии драйвера Node 22.23.5: [усечение дробной задержки](https://github.com/nodejs/node/blob/v22.23.5/lib/internal/timers.js#L344-L348), [целые миллисекунды libuv](https://github.com/nodejs/node/blob/v22.23.5/deps/uv/src/unix/internal.h#L372-L376), [проверка разрешения coarse clock](https://github.com/nodejs/node/blob/v22.23.5/deps/uv/src/unix/linux.c#L1525-L1547). Две операции округления обосновывают допуск 2 мс независимо от найденного минимума.

Исправлен только анализ подписанного сдвига: `-2 <= lagMs < 1000`. Предельное опоздание не изменено. Длительности ответов по-прежнему конечны и неотрицательны. Генератор нагрузки, частота, прогрев, длительность, p95, квоты, состояния, сетевые ограничения и ресурсы сохранены. Тест `signed timer jitter permits only two early milliseconds and retains the late deadline` проверяет все три потока, обе стороны, границы, NaN и бесконечности; весь файл прошёл 3/3.

Первая пара: минимум/максимум сдвига RAG −1,939/+102,935 мс, jobs −0,458/+64,277 мс, customer −0,932/+65,795 мс. В ней не найдено ни значения ниже −2, ни опоздания от 1000 мс. p95 RAG: 211,544 → 257,854 мс при пределе 303,853 мс; индексирование: 1399 → 1347 мс при пределе 3678,8 мс. Другие пары ещё не объявлены принятыми.

Долгий процесс уже загрузил старый анализатор. Его исходный полный raw JSON, вердикт и exit code сохраняются без редактирования. После шести сторон отдельный запуск исправленного анализатора создаёт вторую квитанцию с SHA-256 исходных байт, обеих версий анализатора и собственным вердиктом. Только фактический проход всех правил на полном наборе и независимая проверка могут закрыть NFR-2. Исходный отказ не переименовывается в успех. Приложение и его runtime при этом не пересобираются и не меняются.
