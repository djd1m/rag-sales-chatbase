# Архитектура обновления интерфейса Суфлёра

Черновик для focused QCSD, 25.11.2026. Изменения по замечаниям исходной проверки учтены в проекте. Шаг 5 завершится после независимой сверки нового снимка.

## C4 Context

Владелец сайта использует публичный старт до регистрации и защищённый кабинет после входа. Посетитель взаимодействует с виджетом на разрешённом внешнем сайте. Суфлёр проверяет сайт и читает его через текущую серверную цепочку, обращается к модели с действующими ограничениями. ЮKassa, подтверждение почты и поддержка подключены через контракты customer-trust при готовности интеграции. Граница доверия проходит между браузером и сервером Суфлёра и между сервером и внешними поставщиками. [C4 Context](diagrams/architecture-c4-context.mermaid)

## C4 Container

Действующие Next.js `web` обслуживает серверный рендеринг, UI и API за Caddy `proxy`. Postgres хранит сессии, ботов, источники, задания и их состояние. Redis/BullMQ доставляет задачу `worker-index`; прогресс читается из Postgres. `migrate` остаётся одноразовым исполнителем действующих миграций. Новых контейнеров, фоновых заданий и прямых браузерных запросов к модели здесь нет. [C4 Container](diagrams/architecture-c4-container.mermaid) · [compose.vps.yml](../../compose.vps.yml)

## Sequence flows

- **Сайт и первый ответ.** Форма передаёт адрес в теле POST, единственный действующий запуск получает `202`. Опрос доходит до готовности. Явный вопрос отправляется отдельно. Первый `answered` сразу раскрывает связанную цитату. [Последовательность](diagrams/sequence-happy.mermaid)
- **Сбой чтения.** `robots_disallowed` и `no_text` дают ветки PDF и исправления. При первом временном отказе или `done/site:null` доступен повтор только GET той же задачи. Временный отказ, серверный `no_response` и `404` имеют разные выводы. [Последовательность](diagrams/sequence-error.mermaid)
- **Вход и claim.** Реальный ответ auth/claim со своим контекстом сопровождает переход в текущей вкладке. Кабинет проверяет контекст актуальной серверной сессии и показывает одноразовый исход независимо от готовности. PDF выбирает фактического бота либо просит явно создать его при доступном месте. [Последовательность](diagrams/sequence-claim.mermaid)

## Data and storage

- Для UI не требуются новые таблицы, миграции, серверное хранение файлов или новые события. Auth, квоты, RAG, S3/хранилище файлов и внешний виджет остаются на действующих границах.
- `PreviewStart` валидирует адрес до POST и до записи. Новые ссылки несут только `jobId` или разрешённый режим. Старый единственный `url` в `/preview?url=…` даёт один совместимый автозапуск и удаляется из адресной строки без новой истории. PDF/retry имеют приоритет над `url` и никогда не стартуют. Неподдерживаемый протокол и userinfo дают видимую ошибку. Поддерживаемый path/query живёт только в форме, памяти попытки и теле существующего POST.
- В хранилище вкладки `n6_preview_launch_v2` ограничен 8 элементами и 24 ч. Ключ сопоставления — SHA-256 нормализованного HTTP(S)-origin корневого безопасного URL, значение — случайный UUID и срок. `n6_preview_retry_v2` хранит максимум 8 пар `jobId`/origin до 24 ч и только после `202`. Некорневой адрес не предзаполняется. Старый префикс `n6_preview_key:` очищается, для текущего безопасного точного корневого адреса можно однократно перенести его UUID. При недоступном хранилище сохраняется ключ в памяти текущей формы. Срок, вытеснение и маскирование данных проверяются на маркерах.
- Одноразовый `n6_preview_claim_notice_v1` содержит только разрешённый исход из фактического ответа, его `X-Sufler-Claim-Context` и срок до двух минут. В защищённом dashboard digest вычисляется от идентичности текущей проверенной сессии. Слот потребляется один раз, при отсутствии, ошибке хранения, истечении или несовпадении баннер успеха не выводится. Если подтверждённый отказ auth невозможно передать через slot, он остаётся в форме рядом с явным продолжением. JSON, авторизация и признаки готовности бота сохраняют свои источники. Точные `next` и PDF действуют независимо от наличия уведомления.
- История чата, выбранный ответ и локальные отметки проверки живут в рамках экрана текущего бота или задачи. При `unknown` отображается только доступная серверная информация. Состояние подтверждения ответов принадлежит серверу. Действующие динамические страницы, чтение по сессии и отсутствие общего кэша пользовательских данных сохраняются.

## API design

| Действующий интерфейс | Потребляемый контракт |
|---|---|
| `POST /api/preview` | Поле `url`, `Idempotency-Key`, `202` и `data.index_job_id`. Адрес, бюджет и origin проверяет сервер. |
| `GET /api/preview/[id]` | Состояние задания, счётчики, причина отказа или усечения, при `done` `questions_left` и объект `site` либо `null`. Сервер проверяет cookie и `jobId`. `running`/`no_response` продолжают обычный опрос, `failed`, `done` и `404` останавливают его. При `503` или `done/site:null` ручная проверка выполняет один GET того же ID, открывает чат при восстановившемся `done/site` или возвращает обычный опрос при активном состоянии. |
| `POST /api/preview/[id]/ask`, `POST /api/bots/[botId]/ask` | Серверные `answered` с цитатой, `unknown` с доступным контактом и отдельный квотный отказ. Флаг `first_answer` действующего публичного предпросмотра сохраняет момент появления CTA. |
| `POST /api/auth/login`, `POST /api/auth/register`, `POST /api/preview/[id]/claim` | JSON и HTTP-статусы сохраняются. Валидный ответ с установленным исходом для проверенной сессии дополняется same-origin `X-Sufler-Claim-Context`, HMAC-предназначение `sufler-preview-claim-context-v1`. Auth-контур даёт статус без `bot_id`. Фактическая сессия и операции по-прежнему проверяются сервером. |
| `POST /api/preview/[id]/share`, `POST /api/bots/[botId]/publish` | Первое действие записывает существующий клик и продолжает путь владельца. Публичная страница появляется после отдельного подтверждения. |
| `POST /api/bots`, `POST /api/bots/[botId]/sources` | Явное создание бота и авторизованная загрузка PDF для него. Действующие multipart, ключ идемпотентности и лимиты сохраняются. |
| `POST /api/bots/[botId]/verify`, `/dashboard/bots/[botId]/install` | Серверное включение ответов после проверки и действующий код установки с допусками. Локальные отметки не вызывают `verify` и не свидетельствуют об установке. |
| `/pricing`, `/upgrade?plan=nobadge` или `/upgrade?plan=studio` | Действующие тарифные факты и выбор предложения. Проверки доступа и оплата принадлежат customer-trust. |

Новый точный `next`, режим кабинета и ссылки сохраняют схемы API. Дополнительный заголовок предназначен для изоляции одноразового контекста UI. Он не авторизует запросы, не переносит email и не экспортируется cross-origin. Вход не добавляет значения полей или произвольный URL в редирект. Для PDF действует обычная авторизация. Разница между `first_config` и `first_answer` внешнего виджета сохраняется.

## Observability

- **Журналирование.** Переиспользуются существующие сообщения уровня `error` web о сбое создания предпросмотра, доставки в очередь, сохранения при входе и записи событий CTA. Обновление UI не добавляет сбор URL, текста вопроса, токенов, файлов, email или новых сетевых событий. Контекст диагностики — маршрут, вид отказа и время на тестовом наборе. [preview-handler.ts](../../apps/web/src/server/preview-handler.ts) · [auth-handler.ts:94](../../apps/web/src/server/auth-handler.ts#L94)
- **Два счётчика.** Имеющийся `growth-report` возвращает агрегаты `share_cta_shown` и `share_cta_clicks` за тот же период. Первый берётся из серверной записи первого подходящего ответа, второй из действующего нажатия. Они помогают заметить потерю доступности CTA после успешно обработанных ответов. Они не измеряют геометрию, завершение PDF или качество ответа. Оператор сравнивает значения в сопоставимых окнах и проверяет сценарий на стенде при заметном изменении. [growth.ts:48](../../packages/db/src/growth.ts#L48) · [growth-report.ts](../../packages/db/src/growth-report.ts)
- **Внешний симптом.** После входа пользователь видит обычный кабинет и теряет PDF, повторный экран сам начинает чтение, страница зависает на ожидании либо первый подтверждённый ответ появляется без действующего перехода. Браузерный прогон фиксирует видимый результат и число запросов с синтетическими ответами. Никаких фоновых вопросов, вызовов модели или реальных платежей для диагностики не требуется.
- **Кто замечает.** Владелец UI смотрит сквозные проверки и сообщения поддержки, оператор сверяет ошибки web и агрегаты, customer-trust проверяет ошибки входа и подтверждения. Сохранение файла, подтверждение установки и улучшение конверсии требуют собственных свидетельств. Отдельной телеметрии для них здесь не вводится.

В synthetic fixture воспроизводятся account A/B, владелец с одним и несколькими ботами, достигнутый предел и связанная браузерная сессия. Принадлежность, сессии, provider-independent auth/claim и `POST /api/bots/[botId]/sources` проверяются настоящим сервером. Квитанция теста различает реальный HTTP и контролируемую подмену.

### Воспроизводимое наблюдение установки U09

Владелец UI готовит отдельный стенд с чистой DB и Redis, собирает приложение и настоящий widget bundle. На стенде новый синтетический владелец входит штатным способом. Поток создания бота, готовый источник «Условия доставки», тестовый контакт и отдельный разрешённый origin используют API и тестовые DB seeds по образцу интеграционных тестов. Создаётся и второй владелец для проверки `404`. Необходимые локальные адреса, идентификатор сборки и список подмен записываются в квитанцию. Порты доступны только из изолированного тестового контура браузера. Синтетический провайдер подставляется серверному fetch в тестовом процессе, исходящий доступ к реальным поставщикам заблокирован. Если стартовый probe нужен в этом контуре, он получает тот же локальный fixture. Production/runtime настройки и code paths остаются обычными.

1. В `sufler-ui-audit-browser-1` открыть настоящий `/dashboard/bots/[botId]/install` на пустом контакте (`contact_required`) и после установки тестового контакта (`ready`). Записать тему, viewport, разрешённые домены, видимые инструкции, результат копирования и состояние Copy при отказе clipboard. Свои и чужие идентификаторы проверяются в отдельных контекстах. Ветку `bundle_missing` можно подтвердить отдельной оснасткой и подписать её происхождение.
2. Разместить дословно выданный стендом тег на контролируемой странице другого origin по схеме `widget-harness` (разные hostname или порт). Действительный адрес стенда идёт в CSP. Проверить `config`, внешний вид, открытие чата, допустимый CORS, собственный и неразрешённый origin. Это фактическое браузерное наблюдение заполненного стенда, даже при синтетическом источнике. Копирование, загрузка `config` и заглушка сами по себе не подтверждают работу ответов.
3. В отдельной ветке задать один явный вопрос на разрешённой странице при готовом проверенном боте. Можно использовать синтетический ответ вместо обращения к платному провайдеру. Осмотрит ли источник пользователь и какие `first_config_at`/`first_answer_at` записаны реальными обработчиками для этого origin, фиксируется отдельными результатами. Если локальный fake сформировал ответ, формулировка «внешний виджет работал на изолированном стенде с synthetic model fixture» сохраняет эту границу. Если ответ или серверное событие не получены, в квитанции только фактически наблюдаемые этапы и явный нерешённый пункт.
4. Сохранить дату, revision, browser engine, origins, обезличенные скриншоты заполненного экрана и внешней страницы, результат CSP/CORS и безопасный статус событий. Браузерный component fixture и прежнее чтение кода отдельно подтверждают контракты и не заменяют это обязательное наблюдение. На квитанции сделать отдельное решение о доработке установки. До фактического прогона приёмка FR-9 открыта.
