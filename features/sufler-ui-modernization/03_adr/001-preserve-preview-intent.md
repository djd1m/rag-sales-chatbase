# ADR-001 — Сохранить выбор источника на пути из предпросмотра в кабинет

## Status

`proposed` — переходы обратимы без миграции до или после выпуска. Пересмотреть, если кабинет начнёт требовать подтверждение почты для обычного входа или понадобится восстановление загруженного файла между устройствами.

## Context

Лендинг направляет отправленную форму на `/preview?url=…`, где браузер начинает чтение. Публичный API предпросмотра работает с сайтом. PDF загружает вошедший владелец для конкретного бота из кабинета. При входе и регистрации сервер может сохранить текущий черновик предпросмотра даже после сбоя чтения. Сейчас `safeNextPath` возвращает только подтверждённые формы адресов оплаты и приглашения, а статус задачи чтения не содержит исходный URL для неуспешной задачи. [PreviewStart.tsx](../../../apps/web/src/app/preview/PreviewStart.tsx) · [preview-handler.ts:141](../../../apps/web/src/server/preview-handler.ts#L141) · [auth-handler.ts:94](../../../apps/web/src/server/auth-handler.ts#L94) · [previews.ts:154](../../../packages/db/src/previews.ts#L154)

## Decision Drivers

1. **D1 — высокий.** Доступ и переход после входа должны проверяться сервером. Ссылка не содержит файл, произвольный URL возврата или указание на чужого бота. FR-2, FR-4, NFR-3.
2. **D2 — высокий.** Выбор PDF и возможность исправить адрес сохраняются до следующего шага. Просмотр состояния ничего не запускает. FR-1, FR-2, FR-3, FR-6, NFR-4.
3. **D3 — высокий.** Вход, приглашение, оплата, автосохранение, плановый предел и действующий запуск сайта работают по прежним контрактам. FR-2, FR-3, FR-4, FR-5, C-1, C-2.
4. **D4 — средний.** Снизить объём данных, которые надо хранить и удалять. NFR-3, C-2, C-4.

## Considered Options

### A — Точный внутренний переход и адрес в текущей вкладке

- Плюсы. Выбор источника читается из маршрута, работает с обычным входом, отдельный адрес возврата не несёт файлов и пользовательской ссылки. Для восстановления достаточно данных текущей вкладки и идентификатора задачи.
- Издержки. Клиентские и серверные страницы должны согласовать форму `next`. Очищенное хранилище, открытие из другой вкладки или старый предпросмотр требуют ручного ввода адреса.

### B — Серверный черновик сценария с идентификатором продолжения

- Плюсы. Может пережить смену вкладки или устройства. Создаёт одну точку счёта для многошаговых форм и позволяет управлять сроком жизни на сервере.
- Издержки. Потребует нового API или изменений текущих, привязки черновика к аккаунту, правил TTL и очистки. Решение расширяет состав данных и затрагивает авторизацию и миграции.

### C — Обычный вход и выбор PDF вручную в кабинете

- Плюсы. Минимум изменений в авторизации и навигации. Предел планов и надёжность отправки остаются в действующих обработчиках.
- Издержки. После входа теряется источник. Ради загрузки нужно самостоятельно выяснить, где создать бота и как найти форму. При отказе сайта восстановление введённого адреса отсутствует.

## Decision Matrix

| Драйвер | Вес | A — точный переход | B — серверный черновик | C — обычный кабинет |
|---|---|---|---|---|
| D1 | Высокий | Точный `next` и существующие серверные проверки | Нужны отдельные проверки принадлежности черновика | Существующий вход |
| D2 | Высокий | Выбор сохраняется, адрес восстанавливается в своей вкладке | Возможен перенос между устройствами | Продолжение теряется |
| D3 | Высокий | Существующие API и новый режим кабинета | Изменения хранилища и авторизации | Существующие API, новый путь не обеспечен |
| D4 | Средний | Локальный URL и фиксированный адрес возврата | Сроки хранения и очистка записей | Дополнительных данных нет |

## Decision

Выбрать A. Публичный выбор PDF доступен по `/preview?source=pdf`. Вошедший владелец переходит в `/dashboard?source=pdf`, гость сначала в существующий `/login` с `next=/dashboard?source=pdf`. Страница входа принимает эту точную строку через `safeNextPath` вместе с существующими точными адресами оплаты и приглашения. URL назначения передаёт только выбор PDF. Режим входа, регистрации и поддерживаемого подтверждения почты сохраняет только разрешённое назначение. Email-подтверждение по смежному контракту применяется к новому checkout. Доступ к кабинету PDF следует текущей авторизации.

`/dashboard?source=pdf` использует результат серверного списка. В пустом кабинете пользователь явно создаёт бота существующей формой. В заполненном он выбирает один из доступных ботов либо создаёт нового в пределах плана. Выбор ведёт на стандартный экран бота к существующему полю `source-pdf`. Успешное создание из режима PDF ведёт к тому же полю. После автосохранения кабинет показывает серверное уведомление и действительный список. Для единственного бота можно сразу показать один явный переход к его полю PDF. Создание и загрузка запускаются только явным действием. При регистрации после ошибки чтения сохранение черновика выполняет имеющаяся логика сессии.

### Одноразовый контекст исхода claim

`POST /api/auth/login|register` и действующий explicit claim остаются с прежними JSON и статусами. Если ответ auth содержит фактический известный исход автосохранения для выданной и проверенной сессии либо действительный ответ explicit claim содержит результат для текущей проверенной сессии, ответ `no-store` передаёт `X-Sufler-Claim-Context`. Значение — base64url HMAC-SHA256 от текущего токена сессии на серверном секрете с префиксом `sufler-preview-claim-context-v1` и разделителем NUL. Действительный токен сервер берёт из auth-действия или проверенной cookie, а не из параметров запроса. Общая функция `previewClaimContext` из предлагаемого server-only `apps/web/src/server/preview-claim-context.ts` принадлежит customer-trust. Контекст сериализуется только в защищённом dashboard и соответствующем ответе same-origin. Сырой токен, digest и значения поля в журналировании, аналитике, URL и внешнем CORS-экспорте отсутствуют.

`AuthForm` и `PreviewScreen` принимают только совместимую пару из фактического ответа своих действий — известный статус JSON и корректный заголовок. Для auth это `claimed`, `already_claimed`, `expired`, `not_found`, `plan_limit`, `unavailable`; explicit claim может сохранить успешный результат для кабинета, ошибки остаются видимы на текущем экране. Клиент сохраняет `{ outcome, context, expiresAt }` в одном `sessionStorage` слоте `n6_preview_claim_notice_v1` до двух минут. После записи перед показом кабинет читает актуальную серверную сессию через свежую навигацию, потребляет совпадающий слот один раз и удаляет его до показа. Выход со страницы и восстановление из браузерной истории сбрасывают видимый одноразовый результат. Без доступного хранилища, совпадения или свежего фактического ответа пользователь продолжает к действительному списку ботов без утверждения об успехе. Если запись подтверждённого отказа auth невозможна, `AuthForm` показывает этот отказ рядом с кнопкой явного продолжения к прежнему назначению, включая PDF. `saved`/`preview` в URL не участвуют. Сопоставление служит изоляции контекста UI, а авторизация и факт операции определяются существующим сервером.

Уведомление `claimed` сообщает только «Бот из предпросмотра сохранён в вашем аккаунте». `already_claimed` сообщает о прежнем сохранении своего предпросмотра. `plan_limit`, `unavailable`, `expired` и `not_found` дают соответствующие причины и доступные действия. Готовность материалов, разрешение отвечать, возможность получить код и внешняя установка читаются из UI соответствующего бота. Единственный бот в списке остаётся подходящим для явного выбора PDF, без вывода о том, когда он появился.

### Безопасный запуск и возврат по адресу

Новые формы на `/`, `/preview` и в пустом кабинете передают адрес только в теле явного клиентского `POST /api/preview`. После успешного `202` URL навигации содержит только возвращённый идентификатор задачи. В действующем старом `/preview?url=…` единственный допустимый `url` в режиме сайта сохраняет один совместимый автозапуск. После чтения параметра приложение удаляет его из адресной строки заменой текущей записи истории. Режимы PDF/retry исключают автозапуск даже с добавленным `url`. Указанные пользователем исторические URL могут уже попасть в адрес первого запроса. Новые формы и редиректы их не создают.

До POST и до записи браузер разбирает строку согласованно с текущим форматом URL. Userinfo и недопустимый протокол отклоняются, исходные значения не отражаются в сообщении. Путь и query обычного HTTP(S) остаются допустимыми для штатного POST. В `sessionStorage` попадают только безопасный HTTP(S)-origin корневого адреса без произвольного пути, query или fragment и ограниченные служебные значения. `n6_preview_launch_v2` содержит максимум восемь записей по SHA-256 нормализованного допустимого origin с случайным UUID как значением `Idempotency-Key` и сроком до 24 часов. `n6_preview_retry_v2` содержит максимум восемь записей с ключом `jobId`, значением origin и сроком до 24 часов; контекст добавляется только после принятого `202`. Поддерживаемый адрес, который нельзя представить как безопасный корневой origin, живёт только в форме и памяти текущей попытки. Эта попытка переиспользует тот же ключ при повторе в той же форме. Между загрузками вкладки такой адрес вводится вручную. При отказе хранилища действуют форма и идемпотентный ключ в памяти текущей попытки.

Просроченные и некорректные записи удаляются при доступе, переполнение вытесняет самые старые. При первом открытии формы можно однократно перенести UUID прежнего `n6_preview_key:` лишь для точного совпадения безопасного уже предъявленного корневого URL. Старые ключи с данным префиксом удаляются без копирования адресов и без чтения/вывода значений для остальных записей. Действие «Указать другой адрес» открывает `/preview?retry=<jobId>` и предзаполняет только свежий совпадающий безопасный origin. При отсутствии контекста доступен ручной ввод. Существующая серверная квота, UUID в заголовке и дедупликация сохраняются.

UI отвечает за формы старта, `PreviewScreen`, explicit claim producer, потребление контекста в кабинете и доставку к полю. Customer-trust владеет `AuthForm`, страницей входа, `safeNextPath`, auth producer и общим серверным helper корреляции. Браузерный контракт слота принадлежит UI и переиспользуется формой входа. Файлы оболочки `SiteHeader` и `app/layout.tsx` интегрирует руководитель работ.

## Rationale

- **D1.** Одно точное назначение проверяет вход. Доступ к боту и файлу контролируют уже существующие запросы владельца. Состояние формы даёт удобство ввода и не участвует в проверке доступа.
- **D2.** Режимы выбора и исправления имеют собственные адреса. Сохранённый `jobId` связывает поле с тем предпросмотром, из которого пользователь вернулся.
- **D3.** После auth используется реальный список с фактом автосохранения. Клиент не создаёт ещё одного бота при загрузке страницы. Тот же `POST /api/preview` и ключ обслуживают старый вход по сайту.
- **D4.** Серверный черновик B оправдан для переноса данных между устройствами, которого в текущем объёме нет. Обычный кабинет C дешевле, но теряет выбор и не приводит к доступной загрузке из ошибки.

## Consequences

### Positive

- Выбор источника сохраняется через штатный вход и ведёт к существующей загрузке. Действуют имеющиеся лимиты, защита бота и защита от повторной заявки на чтение.
- Продолжение с PDF подходит для первого и уже заполненного кабинета, включая реально сохранённый черновик.

### Negative / Accepted Downsides

- В другой вкладке исходный адрес может отсутствовать. UI предлагает обычный ввод. Открытие ссылки подтверждения почты на другом устройстве передаёт выбор PDF только если он присутствует в проверенном контексте customer-trust.
- Список дозволенных адресов растёт на один точный вариант. Граница сверяется единым unit-набором, а переход после действительного входа проверяется в локальном приложении.
- Одноразовый исход зависит от current-session контекста и доступной вкладки. Двухминутный срок, совпадение серверной сессии и потребление слота снижают риск устаревшего сообщения. При отказе остаётся обычный кабинет с выбранным режимом. Новый заголовок не меняет публичное JSON-тело или статусы.
- Короткий контекст поддерживает безопасные корневые адреса. Длинный путь или query придётся ввести вручную после перехода. Legacy URL сохраняет совместимость с однократным стартом, но его первоначальный GET уже задан старой ссылкой.

### Follow-up ADRs

- [ADR-002](002-evolve-existing-screens.md) уточняет, как показываются прогресс, отказ и действия продолжения. Для передачи PDF между устройствами нужен отдельный ADR при расширении области.

### After-action Review

- Через месяц после приёмки владелец UI и ответственный за customer-trust проверяют, доходят ли владельцы от выбора PDF до поля файла, сохраняются ли исходы предпросмотра после входа и хватает ли восстановления адреса в своей вкладке.

## Confirmation

- **Method.** Unit-проверка точных допусков плюс браузерный проход реального Next-маршрута с синтетическим пользователем и управляемыми ответами API. После поставки почтового шага его переход играет тот же сквозной сценарий в тестовом контуре.
- **Monitoring.** Прогонять именованные проверки при изменении auth, `next`, запуска или режима кабинета. Контроль количества mutating requests нужен для основного прохода, повторной инициализации и возврата назад.
- **Success metric.** Один совместимый запуск сайта, ноль запусков при выборе PDF, показе ошибки и предзаполнении, ноль неразрешённых переходов и автоматических созданий из PDF-режима. В подготовленных кабинетах путь заканчивается на `source-pdf` ровно для явно выбранного или явно созданного бота.
- **Owner.** UI отвечает за маршрут и запросы в сквозной проверке, customer-trust за unit и шаги входа, регистрации и подтверждения.
