25 ноября 2026, исходный снимок ветки `feat/sufler-ux-customer-trust-20261125`, до работы над продуктовым кодом. Сначала проверены реализация и команды, затем сверены записи автора. Вердикт **требуется исправление до перехода к Step 7**. Выявлены два HIGH и один MEDIUM.

## HIGH 1. Step 6 допускает план без готового OpenSpec change этой фичи

В `tools/feature-process/check-stage.mjs` строки 72–75 запускают только K2 при отсутствии `--change`. При переданном ID скрипт проверяет синтаксис дельты без сверки её принадлежности к фиче и без проверки готовности плана. Проба с собственным S-планом и без change вернула exit 0 и итоговый `stage-artifacts: pass`.

На реальной фиче `sufler-ui-modernization` команда `run openspec validate sufler-ui-modernization --type change --strict --json` вернула exit 0 и `valid: true`. В тот же прогон `run openspec status --change sufler-ui-modernization --json` показала `isPlanningComplete: false`, отсутствующий design и заблокированный tasks. Это наблюдение за двумя OpenSpec-командами. На тот момент сам Step 6 продуктовой фичи ещё не имел готового плана.

**Исправление.** Получать ID из slug либо проверяемой проектной связи. Проверять принадлежность локальному репозиторию и этому change, `isPlanningComplete`, а затем строгую валидацию. Вернуть ошибку при отсутствующей, чужой или незавершённой change. Для проверки использовать две разные фичи и промежуточное состояние с валидной спецификацией и отсутствующим tasks.

## HIGH 2. Итог этапа не привязан к утверждённой классификации и каталогу фичи

В `check-stage.mjs` строки 49–69 доверяют tier из командной строки. В строках 72–89 этот tier определяет обязательность ADR и ideation convergence. Строка 58 разрешает путь относительно cwd или абсолютный путь; собственный барьер для каталога `features/<slug>` и его реальных файлов отсутствует. Часть upstream-проверок дополнительно ограничивает путь, но вызывается лишь на определённых этапах. Наблюдение на безвредной собственной пробе под игнорируемым каталогом checkout: Step 6 вернул `pass` и указал артефакт внутри `.secrets/sufler-process-independent-qp2uwrr4/`. Для того же плана чистый upstream K2 вернул 0 с S и 1 с M. Проверка абсолютных внешних путей основана на чтении кода; к посторонним файлам рецензент не обращался.

**Исправление.** До чтения содержимого разрешать только непосредственный каталог фичи в каноническом `features/` этого checkout. Проверять реальный путь артефактов и символические ссылки. Брать tier из однозначного объявления в Step 0 и отклонять несовпадение. Оставить низкоуровневому K2 возможность явно запускать тестовые фикстуры без выдачи проектного stage receipt. Для K1 в `check-names.mjs:93,106` также следует убрать передаваемый `--project` из обычного проектного запуска либо проверять, что он указывает на этот checkout.

## MEDIUM 1. Guard не охватывает опубликованные артефакты самого процесса

В `architecture/guards/guards.config.json:4` перечислены рабочие деревья приложений, тестов, документов и инструментов. Среди включённых областей отсутствуют `features/`, `openspec/`, `.agents/`, `.codex/config.toml` и `architecture/`. В `architecture/guards/check.mjs:29,65` ошибки чтения обходятся молча. Текущий результат `{"ok":true,"violations":[]}` относится к успешно прочитанным файлам по семи шаблонам секретов.

**Исправление.** Расширить область проверки публикуемыми входами и выходами процесса, обходить только файлы, разрешённые к публикации, вернуть ошибку на недоступном обязательном входе. Проверить синтетический маркер в публикуемом отчёте на фикстуре. Сохранять в диагностике только путь и правило.

## Сверка публикационных исключений, 25 ноября

В начальном staged-снимке все 89 файлов вендорных QE references совпали с установленной поставкой; семь содержали CRLF. Git вернул exit 0 для staged whitespace-проверки. В YAML учебный пример с идентификатором tc005_hardcoded_credentials проверяет обнаружение зашитых учётных данных. Конфигурация Gitleaks применяет к правилу generic-api-key конъюнкцию пути и полного точного значения секретного поля. Контроли с другим значением и с соседним именем файла в исключение не попали. Сверка ограничена публичными данными и синтетическими примерами.

Две границы начального снимка уточнены при проверке. Регулярное выражение пути с префиксом `(^|/)` совпало также с копией дерева под дополнительным каталогом. Атрибут `-whitespace` ограничил whitespace lint вендорным деревом; в изолированной Git-фикстуре checkout с core.autocrlf=true всё ещё преобразовал LF. Чтобы гарантировать ровно один repo-relative путь и побайтный checkout при преобразовании окончаний строк, требуются соответственно якорь от начала пути и локальный атрибут `-text`.

**Итог публикационной сверки — PASS.** В исправленном staged-снимке Git назначил вендорной фикстуре оба атрибута `-text -whitespace`; для проектного README оба остались unspecified. На повторной изолированной пробе checkout с core.autocrlf=true сохранил исходные LF. Правило Gitleaks для repo-relative путей теперь совпало только с исходной парой путь/значение. Вложенная копия дерева, соседний YAML и другое значение дали отрицательный результат. Прежняя allowlist для четырёх тестовых констант совпала с HEAD; staged whitespace-проверка вернула 0. Рецензент независимо проверил конфигурацию и суммарные результаты контрольных сопоставлений. Полный скан публичного снимка проводил автор.
