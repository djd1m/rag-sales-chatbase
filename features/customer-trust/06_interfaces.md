# Канонические интерфейсы между авторами customer-trust

Обязательное дополнение к [Step 6](06_implementation_plan.md) и [владению](06_ownership.md). Сохраняет согласованные контрактные детали до разделённой реализации.

- `@n6/notifications` — приватный workspace Node 22, без Next, PostgreSQL, Redis или новых внешних npm-зависимостей. Root создаёт пакетный манифест, версия `0.1.0`, `dist/index.js` и `dist/index.d.ts`. Автор 1 публикует именованные `readCustomerMailSettings`, `createCustomerMailTransport`, `renderAccountAccessMessage`, `renderPurchaseConfirmation` и типы `CustomerMailSettings`, `CustomerMailMessage`, `CustomerMailResult`, `CustomerMailTransport`. Чтение конфигурации получает явный `{ N6_MAIL_MODE?, N6_RESEND_API_KEY?, N6_MAIL_FROM? }`, возвращает `disabled` либо `resend` с валидными настройками без I/O.
- `CustomerMailMessage = { from, to, subject, text, html? }`. `CustomerMailTransport.send(message, { idempotencyKey? })` возвращает `accepted` с `providerId`, `permanent`, `retryable` или `unknown`. Создание получает server config и инъекцию `fetchImpl` для тестов, без произвольного боевого origin. Worker рендерит исходное письмо по неизменяемым данным покупки до первого допуска, в `sending` commit закрепляет полное тело, включая `from`, и выбранный ключ. Повтор читает сохранённые байты и ключ. Непривязанный к выдаче worker не заполняет динамический `paidUntil`. Verify/reset исходную ссылку держат только в памяти. `packages/db` владеет данными, не импортирует HTTP, worker не импортирует Next/web.
- Новый immutable реестр `trust-legal-catalog.ts`: `readTrustDocument(kind)`, `listTrustDocumentLinks()` и тип `TrustDocumentKind` предоставляют точные `kind, path, version, digest, effectiveAt, title, sections`. `kind` принимает `terms/offer/privacy/consent/cookies/widget-notice`. Клиент получает безопасные props, у API остаётся серверная сверка `terms`, `consent` и `offer_version`. Публичный виджет берёт один `{ text, href }` из реестра через `/w/v1/config`; optional для старых тестовых ответов, только проверенная HTTP(S) ссылка на privacy, без новых cookies.
- Preview: `previewClaimContext(secret, sessionToken)` выдаёт base64url HMAC-SHA256 `sufler-preview-claim-context-v1` + NUL + валидный session token. `X-Sufler-Claim-Context` добавляется только при серверном действительном claim-исходе и сессии, `no-store`, без CORS, логов или URL. Hint `n6_preview_claim_notice_v1`, строго `{outcome,context,expiresAt}`, одноразовый и 2 минуты. Dashboard и явный claim — отдельный UI writer по общему контракту. Реальные `plan_limit/unavailable/expired/not_found` сохраняются на форме с безопасным Continue, если storage недоступен. `saved/preview` из query не доверяются.
- Support использует `BroadcastChannel('n6-auth')`, side channel `n6_auth_epoch` для браузеров без полноценного BroadcastChannel. Сигнал не несёт credentials или account ID. Auth UI публикует успешную смену сессии и reset, root app integration пересылает logout из существующего LogoutButton, автор 2 публикует erasure из AccountScreen. Сценарий без сигналов полагается на authority poll и проверку при возврате. Клиентский shared publisher `customer-auth-signal.ts` принадлежит автору 1.
- Billing UI получает `reconciliation_required` в `CheckoutSnapshot.status`, `succeeded` содержит доказательство применения данного intent, статус действующего account plan оценивается отдельно. `decideReturnState` внутри `payment-return.ts` принадлежит автору 1, потребители в `upgrade` и тесты billing — автору 2. Форма явного действия и `offer_version` остаются у автора 2.
- Runtime общий: root wiring `getRuntime()` отдаёт `mail`, `support`, `payments`, pool/redis/auth; support публичную конфигурацию проецирует своим handler. Номера миграций окончательно разделены: 016 — account proof и legal acceptance, 017 — intent и delivery. У поддержки нет локальных тикетов и своей миграции 018.
