# Можно ли перевести N6 полностью на DeepSeek

Дата проверки: 17.11.2026. Это исследование; провайдер приложения не переключался.
Использованы официальные документы DeepSeek. Реальные API-вызовы и платные пробы
не выполнялись, ключ DeepSeek не использовался.

**Вывод:** генерацию ответов адаптировать можно. Полный существующий RAG только
через официальный API DeepSeek пока не подтверждён: в опубликованном каталоге
не найден endpoint эмбеддингов и соответствующая модель. Отсутствие в документации
не является доказательством отсутствия закрытой/будущей возможности.

## Что подтверждено документацией

- Официальный API принимает `deepseek-flash` и `deepseek-v4-pro`; текущая рекомендация
  документации для Flash — `deepseek-flash`. [Первый вызов](https://api-docs.deepseek.com/en/),
  [модели](https://api-docs.deepseek.com/quick_start/pricing/).
- В Chat Completions `response_format` допускает `text` и `json_object`. Это не
  прямая замена нынешнего запроса с `json_schema` и OpenRouter-specific
  `provider.require_parameters`. [Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/).
- **В Responses API уже документирован `text.format.type=json_schema`.** Поэтому
  для переноса строгого формата разумно рассматривать `/responses`, а не просто
  ослаблять существующий контракт до JSON mode. В ответе другая структура:
  `output` вместо `choices`, отдельный `usage`; нужны адаптер и проверка схемы
  в приложении. [Responses API](https://api-docs.deepseek.com/api/create-response/),
  [руководство](https://api-docs.deepseek.com/guides/responses_api/).
- У JSON mode возможен пустой/пробельный ответ и обрезанный JSON: потребуется
  явный отказ/учтённый повтор. [JSON Output](https://api-docs.deepseek.com/guides/json_mode/).
- В каталоге перечислены чат, Responses, Messages, FIM, модели, файлы, Search/Fetch,
  OCR и аудио. Публичного `/embeddings` там не обнаружено. Search/Fetch не выдаёт
  замену нашим индексируемым векторам. [Каталог API и моделей](https://api-docs.deepseek.com/api/list-models/).

## Что требуется именно нашему проекту

`packages/rag/src/openrouter.ts` сейчас объединяет ответы и эмбеддинги одним ключом
и константой адреса OpenRouter. `constants.ts` и `config.ts` допускают только
`anthropic/claude-haiku-4.5` и `openai/text-embedding-3-small`.
Поэтому смены ключа или имени модели в `.env` недостаточно.

Postgres хранит `vector(1536)`; документы и вопрос должны проходить через одну
совместимую embedding-модель. Замена модели требует переиндексации даже при той же
размерности; смена размерности дополнительно затрагивает миграцию, валидацию и
тесты. Порог сходства 0.40 нужно заново откалибровать, а не считать универсальным.

## Варианты

| Вариант | Оценка |
|---|---|
| DeepSeek для ответов + нынешние эмбеддинги через OpenRouter | Наименьшее изменение индекса: оставить 1536 и существующую embedding-модель. Нужны отдельные ключи/адаптеры, без скрытого переключения провайдера. |
| DeepSeek для ответов + отдельный embedding API | Можно убрать OpenRouter, но это два провайдера. Нужны контрактные тесты выбранного embedding API. |
| DeepSeek для ответов + локальная embedding-модель | Можно обойтись без внешнего embedding API, но это не «только DeepSeek». На VPS с 4 ГБ RAM дополнительную модель нельзя обещать без замеров памяти/скорости; потребуется оценка отдельного ресурса, индекса и переиндексации. |
| Только официальный DeepSeek API для всего нынешнего RAG | Не рекомендован к реализации до подтверждённого embedding endpoint и модели. |

Предпочтительный первый шаг, если владелец выберет DeepSeek: отделить answer и
embedding adapters, добавить явные настройки двух провайдеров, реализовать
Responses-адаптер DeepSeek, сохранить нынешние эмбеддинги. Сохранить неизменными
серверную проверку цитат, отказ «не знаю», квоты, журнал попытки до запроса,
ограниченный повтор и учёт каждого платного вызова.

Проверки будущей реализации: JSON по схеме/пустой/неполный/отказ, выдуманная цитата,
ошибки 401/429/5xx и таймаут, usage, startup probes, индексация → поиск → ответ
на русских материалах и вопросы вне источника. Текущие server startup probes
зависят от OpenRouter и также потребуют изменения. Эти проверки пока не выполнялись.
